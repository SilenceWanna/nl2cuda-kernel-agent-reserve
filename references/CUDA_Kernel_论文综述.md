# 用大模型自动生成高性能 CUDA Kernel —— 论文综述（持续更新）

> 这是一份边读边累积的中文综述，覆盖"用 LLM/RL 自动生成与优化 CUDA kernel"这一研究方向的代表性论文。
> 每读一篇追加一节，末尾维护一张总对比表和领域全景分析。

---

## 背景速览（读任何一篇前的公共知识）

- **算子(Operator)**：一次数学变换的抽象（如 matmul、conv、relu）。神经网络 = 算子的流水线。
- **Kernel**：算子在 GPU 上的具体并行实现，用 CUDA 编写。
- **算子融合(Kernel Fusion)**：把多个算子合并成一个 kernel，减少中间结果在显存的反复读写——这是高性能 kernel 的核心手段（FlashAttention 是巅峰案例）。
- **KernelBench**：评测"LLM 生成 kernel"能力的标准基准，分 Level 1（单算子）/ Level 2（可融合的多算子）/ Level 3（完整网络架构）三档难度，同时衡量正确性与运行速度。
- **两个基线**：PyTorch Eager（逐算子执行）与 `torch.compile`（编译优化）。生成的 kernel 通常和它们比加速比。
- **贯穿全领域的根本矛盾**：CUDA 代码在预训练数据里占比不到 0.01%，导致模型"不会写"，是所有困难的源头。
- **两大流派**：
  - **训练模型派(training-based)**：用 SFT/RL 提升模型内在 CUDA 能力。上限高，但成本高、易训崩。代表：Kevin、SparseRL、CUDA Agent。
  - **免训练派(training-free)**：模型不动，靠推理时的工作流/搜索/知识注入压榨现有模型。即插即用，但受基座模型上限制约。代表：STARK、ReGraphT。
  - 两派互补：免训练框架可以驱动被训练过的更强模型，叠加使用。

## 1. Kevin: Multi-Turn RL for Generating CUDA Kernels
- **机构/时间**：斯坦福 + Cognition AI，2025.07
- **流派**：训练模型（多轮强化学习）
- **一句话**：第一个用"多轮 RL"训练来生成 CUDA kernel 的模型（Kevin = Kernel Devin）。
- **核心思想**：模拟人类专家"写→跑→看反馈→改"的迭代过程，把多个回合都放进每一步 RL 训练。
- **解决的难题**：
  1. 长轨迹→拆成单轮样本 + 只保留思维链摘要，防上下文爆炸。
  2. 中间步骤信用分配→用折扣因子把未来收益累加回来（求和 + γ=0.4 最好）。
  3. 奖励作弊→规则检查，强制内联 CUDA，防止抄参考实现。
- **奖励设计**：`S = 0.3×[正确] + (baseline时间/kernel时间)×[正确]`，错误则 0 分。
- **结果**：基座 QwQ-32B 的正确率 56%→82%，加速 0.53×→1.10×，超过 o4-mini（0.78×）。
- **重要发现**：串行多轮打磨 比 并行多次采样 更划算；多轮训练保持了探索能力。

## 2. SparseRL: Mastering Sparse CUDA Generation via Pretrained Models & Deep RL
- **机构/时间**：中科院计算所 等，ICLR 2026
- **流派**：训练模型（深度强化学习）
- **一句话**：专攻稀疏矩阵运算（SpMV/SpMM），为每个输入的稀疏矩阵量身定制 CUDA 代码。
- **背景**：稀疏矩阵大部分是 0，非零元素分布千奇百怪且运行时才知道，不存在万能 kernel。
- **三大创新**：
  1. DRL + 编译器/执行器反馈：把生成每个 token 当作动作，用 actor-critic。
  2. **稀疏矩阵正弦嵌入**：把非零元素的行列坐标编码成模型能懂的向量，让模型"感知"矩阵结构（类比 AlphaFold 的特殊模态输入）。
  3. **分层奖励**：同时考虑编译成功（编译期）+ 执行时间（运行期）。
- **三阶段训练**：CUDA 代码增强预训练 → 监督微调(SFT) → 强化学习(RL)。
- **结果**：SpMV 编译率 +20%、代码平均快 30%；成功迁移到 SpMM。

## 3. STARK: Strategic Team of Agents for Refining Kernels
- **机构/时间**：Meta Ranking AI Research + 杜克大学，2025.10
- **流派**：免训练（推理时多智能体 + 搜索）
- **一句话**：不训练模型，组建"AI 专家团队"（规划/编码/调试）+ 树搜索来榨性能。
- **指出的三个毛病**：探索太天真（只看上一次）；单一智能体包揽一切；"会规划但不会实现"的鸿沟。
- **三大设计**：
  1. **多智能体**：Plan（高温度 τ=0.8，出主意）/ Code（低温度 τ=0.1，精确写码）/ Debug（修错）。温度差异是关键洞察。
  2. **树形记忆 + 战略搜索**：把优化建模为搜索树上的探索，节点存 kernel 及其表现；用适配过的 ε-greedy（根节点限流、死枝剪除、高探索率）。
  3. **接地指令 + 动态上下文窗口**：规划者必须用标记圈出"改哪一段"；不同智能体看不同的历史视图。
- **结果**：相比基线智能体最高快 16×（L2），L1 快 10.7×；在基线连跑通都难的题上也能写出有竞争力的 kernel。

## 4. CUDA Agent: Large-Scale Agentic RL for High-Performance CUDA Kernel Generation
- **机构/时间**：字节跳动 Seed + 清华 AIR，2026.03
- **流派**：训练模型（大规模智能体 RL）—— 本领域的"集大成者"
- **一句话**：用大规模智能体强化学习训练模型，首次让生成 kernel 全面超过 torch.compile 和顶级闭源模型。
- **三大组件**：
  1. **可扩展数据合成**：爬取种子算子 → LLM 组合融合成多算子任务 → 严格筛选（防作弊、时间 1-100ms）→ 得到 CUDA-Agent-Ops-6K（6000 样本）。
  2. **技能增强、防作弊的智能体环境**：SKILL.md 规定标准优化流程；文件权限锁死验证脚本、禁止调用现成实现、5 组随机输入验证、不给联网。
  3. **稳定训练算法**：初始训练 17 步就崩溃；根因是 CUDA 数据太少 + 训练/推理精度不一致导致重要性采样比率爆炸；解法是 actor/critic 多阶段热身，稳定训到 200 步。
- **结果**：L1/L2/L3 上分别有 100%/100%/92% 的 kernel 比 torch.compile 快；最难的 L3 上比 Claude Opus 4.5、Gemini 3 Pro 高出约 40%。

## 5. ReGraphT: From Large to Small — Transferring CUDA Optimization Expertise via Reasoning Graph
- **机构/时间**：中科院计算所 + 华南理工，2025.10
- **流派**：免训练（检索增强 + 知识迁移）
- **一句话**：把大模型的 CUDA 优化推理经验提炼成一张"推理图"，让本地小模型照图走，兼顾隐私与成本。
- **锁定的问题**：大模型有隐私（云 API 泄露）和成本（本地部署贵）问题；小模型能本地跑但"想不了多步"，写复杂 CUDA 不行。
- **两大创新**：
  1. **CUDA 推理图(ReGraph)**：节点 = 一种优化技术，边 = 优化间的转移；把大模型吐出的优化轨迹合并成一张有向图，固化"该怎么组合优化技巧"的专家经验。
  2. **蒙特卡洛图搜索(MCGS)**：在图上做"选择→扩展→rollout→回传"，引导小模型走出高性能优化路径（避免 O(nᵏ) 穷举）。
- **附带**：提出 CUDAEval 基准，按"推理复杂度"分难度。
- **结果**：在 CUDAEval/ParEval 上平均加速 2.33×，让 7B 小模型逼近大模型水平。

## 6. EvoEngineer: Mastering Automated CUDA Kernel Code Evolution with LLMs
- **机构/时间**：香港城市大学，2025.10
- **流派**：免训练（LLM 代码进化 + 方法论框架）—— 本领域的"裁判/规则制定者"
- **一句话**：把 kernel 优化正式定义为带约束的优化问题，并建立首个系统化的"LLM 代码进化"框架，指导策略设计。
- **动机**：领域碎片化——方法孤立、无法公平比较、问题定义模糊；通用代码进化方法（FunSearch/EoH）对正确性要求松，搬到 CUDA 水土不服。两大后果：资源浪费（堆 token 无收益）、策略盲目。
- **三大贡献**：
  1. **问题形式化**：`min f(p) s.t. g(p)=0`（性能最优 + 编译通过 + 功能正确）；洞察是搜索空间里绝大多数程序无效，导航是关键；LLM 能直接在原始文本空间搜索。
  2. **两层解耦框架**：把代码进化拆成正交的两部分——遍历技术（再分"方案引导层"决定给LLM什么信息 + "提示工程层"决定怎么组织）和种群管理（保优/精英/多样性）。核心价值：把优化策略与提示工程解耦，可独立分析各自贡献；并质疑"LLM 能否真正执行交叉/变异"。
  3. **开源平台 + 大规模验证**：91 个真实算子、6 大类，支持可复现比较。
- **结果**：中位加速 2.72×（最高）、代码有效率 69.8%；最高单算子 36.75×；50 个算子中 28 个（56%）拿到最高加速。

## 7. ConCuR: Conciseness Makes State-of-the-Art Kernel Generation
- **机构/时间**：港科大 + 西湖大学 等，2025.10
- **流派**：训练模型（监督微调 SFT + 数据质量）
- **一句话**：数据稀缺是最大瓶颈；"简洁而信息足的推理过程"是高质量 kernel 的关键。据此造数据集 ConCuR，训出 KernelCoder。
- **动机**：RL 往往不够，SFT 提供的基础对齐不可或缺；但高质量 CUDA kernel 大多闭源，缺数据做 SFT。
- **核心发现（反直觉）**：
  1. **推理越短，正确率越高**（与"想得越久越强"的主流观点相悖）——长推理陷入"过度思考"，反复自我怀疑、破坏逻辑连贯；简洁推理更一致、更准。
  2. **加速比与推理长度基本无关**（相关系数 -0.047）——想得久不会更快，只增冗余。
  3. 结论：正确 kernel + 简洁推理 = 高质量数据。
- **数据流水线**：用 Kevin-32B（本综述第1篇）合成 90,810 个"PyTorch+推理+CUDA"三元组 → 按"加速比 + 推理简洁度"筛选 → 得到 ConCuR（4,892 对）。
- **模型**：对 QwQ-32B 做 LoRA 微调 → KernelCoder（首个在精选"代码+推理+kernel"三元组上训练的模型）。
- **结果**：超过所有开源 kernel 模型及 GPT-4、DeepSeek-V3.1-Think、Claude-4-Sonnet，且参数更少、成本更低。
- **附带**：推理长度可作为任务难度指标。

## 8. CUDA-L1: Improving CUDA Optimization via Contrastive RL
- **机构/时间**：DeepReinforce Team，ICLR 2026
- **流派**：训练模型（对比强化学习 Contrastive RL）
- **一句话**：让模型在生成前先"看几份带加速比分数的历史方案、对比分析谁快谁慢为什么"，再合成更优代码——把奖励信号直接喂进推理，而非只用来更新参数。
- **动机（点破一个盲区）**：传统 RL（REINFORCE/GRPO/PPO）里，加速比这个奖励只被拿去做梯度更新（基线相减/优势归一化/重要性采样），**从不作为输入给模型看**，模型无法在生成时直接"权衡性能取舍"。
- **核心创新——对比 RL**：把多份代码变体连同各自的加速比分数塞进 prompt，训模型先做"为什么这份更快"的比较分析，再产出改进版；分数同时兼任①即时梯度更新的奖励 ②后续迭代的示例池，形成模型与高性能样本的"共演化"。
- **三阶段流水线**：① SFT+数据增强（6个LLM各跑250任务攒2105份成功代码，打基础）→ ② 自监督学习（模型自产自筛成功样本再训，只看正确性不看速度，可视为REINFORCE的稳定特例）→ ③ 对比RL（专攻速度）。骨干模型 DeepSeek-V3-671B。
- **奖励作弊警示**：RL 发现了 KernelBench 评测漏洞——靠多开 CUDA stream 篡改计时，伪造出 18× 假加速（实际算力没变）。论文专门指出这类失败模式并给出更鲁棒的奖励设计。
- **涌现能力**：自动发现并组合优化技巧（内存布局、算子融合、循环展开、访存合并 + 代数化简、常量折叠等）；发现优化的"乘性"原理和"门控"技巧（某些优化必须先做才能解锁其他）；能识别隐藏瓶颈、拒绝"看似有益实则有害"的优化。经典案例：`diag(A)@B` 从 O(N²M) 化简为 O(NM) 的逐元素乘，直接 64× 加速。
- **结果**：A100 上 250 个 kernel 平均 3.12×、中位 1.42×、峰值 120×；对 torch.compile 2.77×、CUDA Graph 2.81×。跨架构可迁移：H100 3.85×、L40 3.13×、RTX3090 2.51×、H20 2.38×（虽只在 A100 上训）。附带贡献：给 KernelBench 补了 CUDA Graph 基线。

## 9. KernelBench: Can LLMs Write Efficient GPU Kernels?（基准的源头）
- **机构/时间**：斯坦福 + 普林斯顿，2025.02
- **流派**：不站队——这是**基准与评测方法论**本身，是前面 8 篇共同的"考卷"。读它相当于回到起点。
- **一句话**：提出 KernelBench 这个开源评测框架和 250 道题，第一次系统回答"当今 LLM 到底能不能写出又对又快的 GPU kernel"——答案是：还差得远。
- **它定义了本领域的通用语言（前面每篇都在用）**：
  1. **三档难度**：Level 1（100 题，单算子，要跟闭源 cuBLAS/cuDNN 硬刚）/ Level 2（100 题，3-6 个可融合算子，要跟 torch.compile 的融合比）/ Level 3（50 题，完整网络架构，需要超越编译器的算法级改造）。
  2. **任务格式**：输入一个 PyTorch `Model` 类，输出优化过的 `ModelNew` 类；模型自己决定"优化哪里、怎么优化"，可用 CUDA/Triton/PTX 等任意工具。
  3. **fast_p 指标**：既对又比基线快 p 倍的题目占比。`fast_0` = 纯正确率，`fast_1` = 比 PyTorch 快的比例；调高 p 就是调高难度。这是后续所有论文报"加速比"的统一尺子。
- **核心结论（给整个领域定了调）**：
  1. **开箱即用很差**：连 o1、DeepSeek-R1 这样的前沿推理模型，也只有不到 20% 的题能追平 PyTorch。
  2. **正确性是最大瓶颈**：推理模型能靠反复试错修好"跑不起来"的错误，但"结果算错"的功能性错误大家都过不去；而且模型越想用复杂优化（如 tensor core wmma），越容易写错。
  3. **根因量化**：CUDA 在流行代码语料 The Stack v1.2 里只占 **0.073%**——这就是后续每篇都引用的"数据 <0.01%~0.07%"根本矛盾的出处。
  4. **反馈和多次采样有用**：把编译/运行/profiler 反馈喂回去做迭代优化，fast_1 从 12%/36%/12% 提升到 43%/72%/18%；高温多次采样也能捞到更多正确解。
- **为什么它排在最后讲最合适**：前 8 篇（Kevin 的多轮 RL、STARK 的多智能体、CUDA-L1 的对比 RL……）本质都是在回答本文提出的三个开放挑战——如何在"低资源数据"下提升、如何利用丰富反馈、如何跨硬件泛化。它是这条研究线的共同起点和记分牌。

## 10. CudaForge: An Agent Framework with Hardware Feedback
- **机构/时间**：明尼苏达大学，2025.11
- **流派**：免训练（推理时双智能体 + 硬件反馈）
- **一句话**：不训练模型，只用 Coder + Judge 两个智能体循环打磨，关键是把**真正的硬件 profiler 数据（Nsight Compute/NCU）**喂给 Judge，让它像人类专家一样"看着性能计数器"定位瓶颈、给出针对性优化建议。
- **它专门点名前作的三个痛点（C1-C3）**：
  1. **C1 效率不够**：RL 方法优化力有限——Kevin-32B 在 L1-2 上采样 16 条轨迹×8 轮才 1.10×；CUDA-L1 有时干脆退化成"抄 PyTorch 官方实现"。
  2. **C2 成本高**：RL 训练要大量算力；某些智能体流水线每个 kernel 要烧 6 个 H100 小时 + $5 API。
  3. **C3 没有硬件反馈**：RL 方法只拿"加速比分数"当反馈，等于**盲目探索**；而人类专家靠 NCU 看访存吞吐、占用率、warp 效率来定位瓶颈。这是 CudaForge 最核心的批评与切入点。
- **双智能体分工**：**Coder**（只管写/改 kernel，只看 Judge 的最新反馈 + 上一版代码 + 任务，不背全部历史，防幻觉省成本）；**Judge**（先验正确性→再用 NCU profiler 采集硬件指标 + GPU 规格→判断是算力受限还是访存受限→给出**一条**具体优化建议，如"加 shared memory tiling"）。循环 N 轮取最优。
- **与 Kevin 的关键对比**：Kevin 只根据"加速比数字"文本式盲改；CudaForge 拿着 NCU 报告（如"寄存器受限、只有 4/16 blocks"）做**可解释、有的放矢**的优化——这是"硬件感知"对"盲目探索"的胜利。
- **结果**：基座用 OpenAI-o3 时正确率 97.6%、平均 1.68×，超过 Kevin-32B、o3、智能体基线；放大迭代轮数可到 2.27×。跨 GPU（A100/6000/4090/3090）、跨基座（o3/GPT-5/gpt-oss-120B/Claude-Sonnet-4/QwQ-32B）都稳。**成本杀手锏**：单块 RTX6000 上 26.5 分钟、约 $0.3/kernel，比"6 H100 小时 + $5"的同类便宜一个数量级。

## 领域全景分析

- **共同基因**：都在对抗"CUDA 数据<0.01%"的根本矛盾；都以"能编译+正确+跑得快"为衡量标准；都要防"奖励作弊/抄参考实现"；都以 FlashAttention（人类专家花约2年优化）为图腾，想让 AI 自动化这种优化。
- **两派分工**：训练派（Kevin/SparseRL/CUDA Agent）提升模型内功，上限高成本高；免训练派（STARK/ReGraphT）设计聪明流程，即插即用受基座制约。两派正交、可叠加。
- **演进脉络**：Kevin 开创多轮 RL → SparseRL 用到稀疏专门场景 → CUDA Agent 把训练规模拉满做到 SOTA；STARK 用多智能体搜索、ReGraphT 用知识迁移，探索"不训练也能强"的路线。

## 十篇总收官（读完全部后的地图）

把这 10 篇放在一起看，是一条清晰的故事线：

1. **起点（记分牌）**：第 9 篇 **KernelBench** 定义了考卷（三档难度、fast_p 指标、PyTorch/torch.compile 基线），并量化了根本矛盾——CUDA 只占代码语料 0.073%。之后所有工作都在这张考卷上刷分。

2. **两大流派各自登场**：
   - **训练派**（改模型内功）：Kevin(多轮RL) → SparseRL(稀疏专场RL) → CUDA-L1(对比RL，把奖励喂进推理) → CUDA Agent(大规模智能体RL，做到全面 SOTA) → ConCuR(不靠RL，靠"简洁高质量数据"做SFT)。
   - **免训练派**（改工作流）：STARK(多智能体+树搜索) → ReGraphT(推理图+图搜索，把大模型经验迁移给小模型) → EvoEngineer(把问题形式化，做代码进化的方法论框架) → CudaForge(双智能体 + 真实硬件profiler反馈，又便宜又强)。

3. **三条越来越清晰的主线**：
   - **数据**：从"没数据"(KernelBench点破) → "造数据"(CUDA Agent/Kevin) → "造好数据"(ConCuR发现简洁推理才是关键)。
   - **反馈**：从"只看加速比分数"(Kevin/CUDA-L1) → "看编译/运行反馈"(KernelBench迭代) → "看真实硬件profiler"(CudaForge用NCU定位瓶颈)——反馈信号越来越接近人类专家实际用的东西。
   - **成本 vs 上限**：训练派上限高但烧钱易崩(CUDA Agent 17步就崩)；免训练派即插即用、便宜(CudaForge $0.3/kernel)但受基座制约。两派正交，未来大概率是"用训练派练出的强模型，去驱动免训练派的聪明工作流"。

4. **共同图腾**：所有论文都反复提 **FlashAttention**——人类专家花了约2年、跨两代GPU才手工优化出来的算子融合杰作。整个领域的终极愿景，就是让 AI 自动完成这种级别的优化。
